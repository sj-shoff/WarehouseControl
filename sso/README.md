# SSO Service

[![Go Version](https://img.shields.io/badge/Go-1.24+-00ADD8?style=flat&logo=go)](https://golang.org/)
[![PostgreSQL](https://img.shields.io/badge/PostgreSQL-16+-336791?style=flat&logo=postgresql)](https://www.postgresql.org/)
[![gRPC](https://img.shields.io/badge/gRPC-1.60+-brightgreen)](https://grpc.io/)

**SSO Service** — централизованный микросервис аутентификации и управления доступом на базе gRPC. Предназначен для выдачи JWT-токенов, управления пользователями, ролями и сессиями для всех подключённых приложений системы.

---

## Описание

Сервис реализует полный цикл аутентификации:
- регистрация пользователей;
- вход в систему;
- обновление токенов;
- управление ролями.

Учётные данные хранятся в изолированной базе данных PostgreSQL.  
Пароли хэшируются **bcrypt**, токены подписываются **HS256**.

Поддерживается многоприложенческая архитектура: каждое подключённое приложение регистрируется в таблице `apps` и получает уникальный идентификатор и секретный ключ. Пользователи привязываются к конкретному приложению, что обеспечивает полную изоляцию данных между разными системами.

---

## Архитектура

### База данных

Три основные таблицы:

- **`apps`** — реестр подключённых приложений: `id`, `name` (уникальное), `secret` (для верификации запросов).
- **`users`** — учётные записи пользователей: `id`, `username`, `password_hash`, `role`, `app_id`, временные метки. Уникальность обеспечивается парой `(username, app_id)`.
- **`refresh_tokens`** — хранилище активных сессий: `id`, `user_id`, `token_hash` (SHA256), `app_id`, `expires_at`, `created_at`. Токены хранятся только в виде хэша.

### Механизм работы с токенами

- При успешной аутентификации сервис выдаёт пару токенов.
- **Access токен** содержит claims: `user_id`, `username`, `role`, `app_id`. Время жизни — 24 часа (настраивается).
- **Refresh токен** — UUID, хранится в БД в хэшированном виде. Время жизни — 30 дней (настраивается).
- При обновлении токенов старый refresh токен удаляется и выдаётся новый (rotation токенов).

### gRPC Interceptors

- **UnaryAdminInterceptor** защищает методы регистрации (`Register`) и изменения ролей (`UpdateUserRole`).
- Проверяет наличие заголовка `authorization` в метаданных, валидирует JWT и убеждается, что роль пользователя — `admin`.
- При нарушении возвращается код `PermissionDenied`.

## Конфигурация

Все настройки передаются через переменные окружения. Файл `.env` должен находиться в корне сервиса.

### Переменные окружения

- `POSTGRES_HOST` — хост базы данных. Для Docker используется `sso-db`.
- `POSTGRES_PORT` — порт базы данных внутри контейнера (по умолчанию `5432`).
- `POSTGRES_EXTERNAL_PORT` — порт базы данных для внешнего подключения (используется для миграций, по умолчанию `5433`).
- `POSTGRES_USER` — пользователь базы данных (по умолчанию `postgres`).
- `POSTGRES_PASSWORD` — пароль базы данных (обязателен).
- `POSTGRES_DB_SSO` — имя базы данных сервиса (по умолчанию `sso`).
- `POSTGRES_MAX_OPEN_CONNS` — максимальное количество открытых соединений (по умолчанию `10`).
- `POSTGRES_MAX_IDLE_CONNS` — максимальное количество неактивных соединений (по умолчанию `5`).
- `POSTGRES_CONN_MAX_LIFETIME` — время жизни соединения (по умолчанию `5m`).
- `GRPC_PORT` — порт gRPC сервера (по умолчанию `44044`).
- `GRPC_TIMEOUT` — таймаут gRPC соединений (по умолчанию `10s`).
- `JWT_SECRET` — секретный ключ для подписи JWT токенов (должен совпадать с ключом в Warehouse Control).
- `JWT_ACCESS_TOKEN_TTL` — время жизни access токена (по умолчанию `24h`).
- `JWT_REFRESH_TOKEN_TTL` — время жизни refresh токена (по умолчанию `720h`).
- `RETRIES_ATTEMPTS` — количество попыток при ошибке БД (по умолчанию `3`).
- `RETRIES_DELAY_MS` — задержка между попытками в миллисекундах (по умолчанию `100`).
- `RETRIES_BACKOFF` — множитель экспоненциальной задержки (по умолчанию `1.5`).

## Установка и запуск

### Требования

- Go 1.24+
- Docker & Docker Compose
- PostgreSQL клиент (для миграций)

### Запуск через Docker

1. Создайте файл `.env` на основе `.env.example`.
2. Запустите сервис и базу данных:
   ```bash
   make docker-up
   ```
3. Дождитесь готовности базы данных (healthcheck).
4. Примените миграции:
   ```bash
   make migrate-up
   ```
5. Сервис автоматически выполнит `InitialBootstrap` при первом запросе от клиентского приложения (например, Warehouse Control), создав запись приложения и пользователя `admin`.

### Сборка бинарного файла

```bash
make build
```
Бинарный файл будет размещён в `bin/sso`.

## gRPC API

Сервис реализует интерфейс `sso.Auth`. Все методы описаны в protobuf спецификации в отдельном [репозитории](https://github.com/sj-shoff/sso_proto).

### `InitialBootstrap`

Инициализация приложения. Вызывается клиентским сервисом при первом запуске. Создаёт запись приложения в таблице `apps` и пользователя `admin`, если они не существуют.

- **Входные параметры:** `app_name`, `app_secret`, `admin_user`, `admin_pass`
- **Выходные параметры:** `app_id`, `admin_id`

### `Login`

Аутентификация пользователя. Проверяет имя пользователя, пароль, идентификатор приложения и секрет приложения.

- **Входные параметры:** `username`, `password`, `app_id`, `app_secret`
- **Выходные параметры:** `access_token`, `refresh_token`, `expires_at`, `role`, `username`
- **Ошибки:** `InvalidCredentials` (неверные данные), `InvalidInput` (отсутствуют обязательные поля)

### `Refresh`

Обновление пары токенов. Принимает refresh-токен и идентификатор приложения. Проверяет валидность токена в БД, удаляет старую запись и создаёт новую.

- **Входные параметры:** `refresh_token`, `app_id`
- **Выходные параметры:** `access_token`, `refresh_token`
- **Ошибки:** `InvalidCredentials` (истёкший или неверный токен)

### `Register`

Регистрация нового пользователя. Требует прав администратора.

- **Входные параметры:** `username`, `password`, `role`, `app_id`
- **Выходные параметры:** `user_id`
- **Ошибки:** `UserExists` (пользователь уже существует), `AdminPrivilege` (недостаточно прав)

### `GetUsers`

Получение списка всех пользователей приложения.

- **Входные параметры:** отсутствуют
- **Выходные параметры:** `users` (массив `{id, username, role}`)

### `UpdateUserRole`

Изменение роли пользователя. Требует прав администратора.

- **Входные параметры:** `user_id`, `new_role`
- **Выходные параметры:** отсутствуют
- **Ошибки:** `UserNotFound` (пользователь не найден), `InvalidInput` (неверная роль)

## Безопасность

- **Хэширование паролей** — bcrypt с cost factor по умолчанию. При аутентификации используется `CompareHashAndPassword`.
- **Хранение refresh-токенов** — хранятся только в виде SHA256 хэша. Даже при компрометации БД злоумышленник не сможет использовать украденные хэши для входа.
- **Защита методов** — методы `Register` и `UpdateUserRole` защищены gRPC interceptor’ом, проверяющим JWT и роль `admin`.

## Логирование

Используется `zerolog` для структурированного логирования.

- **INFO** — успешные операции аутентификации, запуск/остановка сервиса.
- **WARN** — попытки входа с неверными данными, истёкшие токены, подозрительная активность.
- **ERROR** — ошибки базы данных, сбои gRPC, критические ошибки приложения.
- **DEBUG** — детальная отладка (отключается в production).

## Миграции

Управление миграциями осуществляется через [goose](https://github.com/pressly/goose). Файлы лежат в `migrations/`.

- `make migrate-up` — применить все миграции.
- `make migrate-down` — откатить последнюю миграцию.

Миграции создают таблицы `apps`, `users`, `refresh_tokens` и необходимые индексы.

## Устранение неполадок

- **`failed to bootstrap`** — проверьте, что Warehouse Control отправляет правильный `SSO_APP_SECRET`, и он совпадает с записанным в БД (или переданным при первом запуске). Убедитесь, что порт `44044` доступен.
- **`invalid credentials` при логине** — пользователь должен быть создан для правильного `app_id` (данные изолированы по приложениям). Проверьте соответствие пароля хэшу в БД.
- **`connection refused` к БД** — в Docker убедитесь, что сервис зависит от `sso-db` и ожидает `condition: service_healthy`. Проверьте переменные `POSTGRES_HOST` и `POSTGRES_PASSWORD`. При локальной разработке проверьте, что БД запущена на порту `POSTGRES_EXTERNAL_PORT`.
- **`token validation failed`** — проверьте совпадение `JWT_SECRET` в SSO и Warehouse Control, а также синхронизацию времени на серверах.

## Команды Makefile

- `make run` — запуск сервиса локально (требуется БД)
- `make build` — компиляция бинарного файла в `bin/sso`
- `make docker-up` — запуск контейнеров (сервис + БД)
- `make docker-down` — остановка контейнеров
- `make migrate-up` — применение миграций
- `make migrate-down` — откат последней миграции
- `make lint` — запуск линтера (golangci-lint)

## Взаимодействие с Warehouse Control

- Warehouse Control подключается к SSO через gRPC-клиент.
- Адрес сервиса указывается в переменной `SSO_GRPC_ADDR`.
- Для Docker сети используется адрес `sso:44044`.
- При запуске Warehouse Control вызывает `InitialBootstrap` для регистрации приложения и создания администратора.
- Все запросы аутентификации проксируются через SSO.
