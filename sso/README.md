# SSO Service

Централизованный микросервис аутентификации и управления доступом на базе gRPC. Предназначен для выдачи JWT-токенов, управления пользователями, ролями и сессиями для всех подключённых приложений системы.

## Описание

Сервис реализует полный цикл аутентификации: регистрация пользователей, вход в систему, обновление токенов, управление ролями. Все учетные данные хранятся в изолированной базе данных PostgreSQL. Пароли хэшируются алгоритмом bcrypt, токены подписываются HS256.

Сервис поддерживает многоприложенческую архитектуру — каждое подключённое приложение регистрируется в таблице apps и получает уникальный идентификатор и секретный ключ. Пользователи привязываются к конкретному приложению, что обеспечивает изоляцию данных между разными системами.

## Архитектура

### База данных

Сервис использует три основные таблицы в PostgreSQL:

- apps — реестр подключённых приложений. Содержит идентификатор, уникальное имя приложения и секретный ключ для верификации запросов.

- users — учетные записи пользователей. Содержит идентификатор, имя пользователя, хэш пароля, роль, идентификатор приложения и временные метки создания и обновления. Уникальность обеспечивается парой username и app_id.

- refresh_tokens — хранилище активных сессий. Содержит идентификатор, идентификатор пользователя, хэш refresh-токена, идентификатор приложения, время истечения и время создания. Токены хранятся только в виде SHA256 хэша для безопасности.

### Механизм работы с токенами

- При успешной аутентификации сервис выдаёт пару токенов.

- Access токен содержит claims с идентификатором пользователя, именем, ролью и идентификатором приложения. Время жизни access токена составляет 24 часа.

- Refresh токен представляет собой UUID, хранится в базе данных в хэшированном виде и действует 30 дней.

- При обновлении токенов старый refresh токен удаляется из базы данных и выдаётся новый. Это обеспечивает rotation токенов и снижает риски при компрометации.

### gRPC Interceptors

- Сервис использует UnaryAdminInterceptor для защиты методов регистрации и изменения ролей.

- Интерцептор проверяет наличие заголовка authorization в metadata запроса, валидирует JWT токен и убеждается что роль пользователя равна admin.

- Запросы без токена или с недостаточными правами отклоняются с кодом PermissionDenied.

## Конфигурация

Все настройки передаются через переменные окружения. Файл .env должен находиться в корне сервиса.

### Переменные окружения

- POSTGRES_HOST — хост базы данных. Для Docker используется sso-db, для локальной разработки localhost.

- POSTGRES_PORT — порт базы данных внутри контейнера. Значение по умолчанию 5432.

- POSTGRES_EXTERNAL_PORT — порт базы данных для внешнего подключения. Используется для миграций. Значение по умолчанию 5433.

- POSTGRES_USER — пользователь базы данных. Значение по умолчанию postgres.

- POSTGRES_PASSWORD — пароль базы данных.

- POSTGRES_DB_SSO — имя базы данных сервиса. Значение sso.

- POSTGRES_MAX_OPEN_CONNS — максимальное количество открытых соединений. Значение по умолчанию 10.

- POSTGRES_MAX_IDLE_CONNS — максимальное количество неактивных соединений. Значение по умолчанию 5.

- POSTGRES_CONN_MAX_LIFETIME — время жизни соединения. Значение по умолчанию 5m.

- GRPC_PORT — порт gRPC сервера. Значение по умолчанию 44044.

- GRPC_TIMEOUT — таймаут gRPC соединений. Значение по умолчанию 10s.

- JWT_SECRET — секретный ключ для подписи JWT токенов. Должен совпадать с ключом в Warehouse Control.

- JWT_ACCESS_TOKEN_TTL — время жизни access токена. Значение по умолчанию 24h.

- JWT_REFRESH_TOKEN_TTL — время жизни refresh токена. Значение по умолчанию 720h.

- RETRIES_ATTEMPTS — количество попыток при ошибке БД. Значение по умолчанию 3.

- RETRIES_DELAY_MS — задержка между попытками в миллисекундах. Значение по умолчанию 100.

- RETRIES_BACKOFF — множитель экспоненциальной задержки. Значение по умолчанию 1.5.

## Установка и запуск

### Требования

- Go версии 1.24 или выше для локальной разработки.

- Docker и Docker Compose для контейнеризированного запуска.

- PostgreSQL клиент для применения миграций.

### Запуск через Docker

- Создайте файл .env в папке сервиса на основе .env.example.

- Запустите сервис и базу данных командой make docker-up.

- Дождитесь готовности базы данных по healthcheck.

- Примените миграции для создания таблиц командой make migrate-up.

- Сервис автоматически выполнит InitialBootstrap при первом запросе от клиентского приложения и создаст запись приложения и пользователя admin.

### Локальная разработка

- Запустите базу данных отдельно через Docker на порту 5433.

- Обновите переменные POSTGRES_HOST и POSTGRES_EXTERNAL_PORT в файле .env.

- Примените миграции командой make migrate-up.

- Запустите сервис командой make run.

### Сборка бинарного файла

- Для создания исполняемого файла выполните make build.

- Бинарный файл будет размещён в папке bin/sso.

## gRPC API

Сервис реализует интерфейс sso.Auth. Все методы описаны в protobuf спецификации.

### InitialBootstrap

- Метод инициализации приложения. Вызывается клиентским сервисом при первом запуске.

- Создаёт запись приложения в таблице apps и пользователя admin в таблице users если они не существуют.

- Входные параметры: app_name, app_secret, admin_user, admin_pass.

- Выходные параметры: app_id, admin_id.

### Login

- Метод аутентификации пользователя. Проверяет имя пользователя, пароль, идентификатор приложения и секрет приложения.

- При успехе выдаёт пару токенов.

- Входные параметры: username, password, app_id, app_secret.

- Выходные параметры: access_token, refresh_token, expires_at, role, username.

- Ошибки: InvalidCredentials при неверных данных, InvalidInput при отсутствии обязательных полей.

### Refresh

- Метод обновления пары токенов. Принимает refresh токен и идентификатор приложения.

- Проверяет валидность токена в базе данных, удаляет старую запись и создаёт новую.

- Входные параметры: refresh_token, app_id.

- Выходные параметры: access_token, refresh_token.

- Ошибки: InvalidCredentials при истёкшем или неверном токене.

### Register

- Метод регистрации нового пользователя. Требует прав администратора.

- Создаёт запись пользователя в таблице users с хэшированным паролем.

- Входные параметры: username, password, role, app_id.

- Выходные параметры: user_id.

- Ошибки: UserExists при наличии пользователя, AdminPrivilege при отсутствии прав.

### GetUsers

- Метод получения списка всех пользователей приложения.

- Возвращает массив записей с идентификатором, именем и ролью.

- Входные параметры: отсутствуют.

- Выходные параметры: users.

### UpdateUserRole

- Метод изменения роли пользователя. Требует прав администратора.

- Входные параметры: user_id, new_role.

- Выходные параметры: отсутствуют.

- Ошибки: UserNotFound при отсутствии пользователя, InvalidInput при неверной роли.

## Безопасность

### Хэширование паролей

- Все пароли хэшируются через bcrypt с cost factor по умолчанию.

- При аутентификации используется CompareHashAndPassword для верификации.

### Хранение токенов

- Refresh токены никогда не хранятся в открытом виде.

- В базе данных сохраняется SHA256 хэш токена.

- При компрометации базы данных злоумышленник не сможет использовать украденные хэши для входа.

### Защита методов

- Методы Register и UpdateUserRole защищены через gRPC interceptor.

- Проверка токена происходит на уровне сервера до вызова бизнес-логики.

## Логирование

Сервис использует zerolog для структурированного логирования.

- Уровень INFO — успешные операции аутентификации, запуск сервиса, завершение работы.

- Уровень WARN — попытки входа с неверными данными, истёкшие токены, подозрительная активность.

- Уровень ERROR — ошибки базы данных, сбои gRPC, критические ошибки приложения.

- Уровень DEBUG — детальная отладка, отключается в production.

## Миграции

Миграции управляются через goose. Файлы миграций находятся в папке migrations.

- Команда make migrate-up применяет все новые миграции.

- Команда make migrate-down откатывает последнюю миграцию.

- Миграции создают таблицы apps, users, refresh_tokens и необходимые индексы.

## Troubleshooting

### Ошибка failed to bootstrap

- Проверьте что Warehouse Control отправляет правильный SSO_APP_SECRET.

- Значение должно совпадать с тем что записано в базе данных apps или передано при первом запуске.

- Проверьте доступность порта 44044.

### Ошибка invalid credentials при логине

- Проверьте что пользователь создан для правильного app_id. Пользователи изолированы по приложениям.

- Убедитесь что пароль соответствует хэшу в базе данных.

### Ошибка connection refused к базе данных

- В Docker убедитесь что сервис зависит от sso-db и ожидает condition service_healthy.

- Проверьте переменные POSTGRES_HOST и POSTGRES_PASSWORD.

- Для локальной разработки проверьте что база данных запущена на порту POSTGRES_EXTERNAL_PORT.

### Ошибка token validation failed

- Проверьте что JWT_SECRET совпадает в SSO и Warehouse Control.

- Проверьте что время на сервере синхронизировано.

## Makefile команды

- make run — запуск сервиса локально. Требует запущенной базы данных.

- make build — компиляция бинарного файла в bin/sso.

- make docker-up — запуск сервиса и базы данных через Docker Compose.

- make docker-down — остановка и удаление контейнеров.

- make migrate-up — применение всех миграций базы данных.

- make migrate-down — откат последней миграции.

- make lint — запуск golangci-lint для проверки кода.

## Взаимодействие с Warehouse Control

- Warehouse Control подключается к SSO через gRPC клиент.

- Адрес сервиса указывается в переменной SSO_GRPC_ADDR.

- Для Docker сети используется адрес sso:44044.

- При запуске Warehouse Control вызывает InitialBootstrap для регистрации приложения и создания администратора.

- Все запросы аутентификации проксируются через SSO.
